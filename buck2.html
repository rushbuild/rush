Rush vs Buck2.

Choose a build-rule ecosystem first. Both engines use Rust, Starlark, incremental state and cached outputs. Rush explores Bazel-style workspace compatibility and external build-graph replay. Buck2 supplies its own rule APIs around a dynamic incremental engine.

Use this comparison to plan an evaluation. Check compatibility and output correctness before using a timing result to choose an engine.

Remote execution · one shared backend protocol

Send the work to a worker.

Both engines build the same small C++ program through NativeLink 1.8.3. Use two libraries, two headers per library and one executable. Select the same GCC 15.3 worker and eight CPUs; check the executable prints the expected content-dependent result. These checks establish interoperability and output correctness. Validate file actions.

Rush passes 16 action checks in each host direction: execute, cache restore, input changes, a 4 MiB transfer, rejected paths and symlinks, command failures and timeouts. Native C++ builds pass nine checks per direction.

Check device execution separately.

A remote CUDA action allocates, fills and reads back 1 MiB with verified bytes. HIP enumeration succeeds in a restricted worker, but memory initialization fails. HIP remains unqualified. Buck2 GPU actions and full TensorFlow, Modular or Linux remote builds remain unrun.

Provision and isolate the whole worker service, including its output collector. Pin toolchain properties and bound scratch storage. Read setup, trust boundaries and current limits before connecting a workspace.
